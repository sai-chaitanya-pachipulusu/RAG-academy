## Core idea

### The retrieval-rerank pattern

Retrieval optimizes for **recall** (don't miss anything).
Reranking optimizes for **precision** (put the best at the top).

```
Query
  ↓
Retrieve top-50/100 (fast, high recall, lower precision)
  ↓
Rerank to top-5/10 (slower, higher precision)
  ↓
Generate answer
```

### Why reranking matters

From the [Lost in the Middle paper](https://arxiv.org/abs/2307.03172): LLMs struggle when relevant information is buried in the context. Reranking ensures the **best evidence is at the top**.

### Bi-encoder vs Cross-encoder

| Aspect           | Bi-encoder (Retrieval)           | Cross-encoder (Rerank)    |
| ---------------- | -------------------------------- | ------------------------- |
| **How it works** | Encode query and docs separately | Encode query+doc together |
| **Speed**        | Fast (precompute doc embeddings) | Slow (N forward passes)   |
| **Accuracy**     | Good recall                      | Better precision          |
| **Use case**     | First-stage retrieval            | Second-stage reranking    |

**Cross-encoder** sees the query and document together, allowing fine-grained attention:

```python
# Bi-encoder (retrieval)
query_emb = encode(query)
doc_emb = encode(doc)  # Can be precomputed
score = cosine_similarity(query_emb, doc_emb)

# Cross-encoder (rerank)
score = model.predict([query, doc])  # Must be computed at query time
```

### Reranking methods compared

| Method            | Quality   | Latency     | Cost        | Best For                      |
| ----------------- | --------- | ----------- | ----------- | ----------------------------- |
| **Cross-encoder** | High      | +100-300ms  | Medium      | Default production choice     |
| **ColBERT**       | High      | +50-150ms   | Infra-heavy | Large corpora, speed-critical |
| **LLM rerank**    | Very high | +500-2000ms | High        | Hard queries, low volume      |
| **Cascade**       | Tunable   | Tunable     | Tunable     | Latency-sensitive systems     |

### Cross-encoder reranking

The most common production pattern:

```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder('cross-encoder/ms-marco-MiniLM-L-6-v2')

def rerank(query: str, candidates: List[str], top_k: int = 10) -> List[str]:
    """Rerank candidates using cross-encoder."""
    pairs = [[query, doc] for doc in candidates]
    scores = reranker.predict(pairs)

    # Sort by score descending
    ranked = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)
    return [doc for doc, score in ranked[:top_k]]
```

### Neural Reranker Paradigms: Pointwise, Pairwise, Listwise

Neural rerankers are classified into three methodological paradigms based on how they evaluate relevance:

| Paradigm      | Model Examples                                                                           | How It Works                                             | Tradeoffs                             |
| ------------- | ---------------------------------------------------------------------------------------- | -------------------------------------------------------- | ------------------------------------- |
| **Pointwise** | [monoBERT](https://arxiv.org/abs/1910.14424)                                             | Score each query-doc pair independently                  | High quality, slow (N forward passes) |
| **Pairwise**  | [duoBERT](https://arxiv.org/abs/1910.14424)                                              | Compare pairs of documents: "Is A more relevant than B?" | Better fine-grained distinctions      |
| **Listwise**  | [ListBERT](https://arxiv.org/abs/2206.15198), [ListT5](https://arxiv.org/abs/2402.15838) | Consider full list of documents together                 | Best for zero-shot, state-of-the-art  |

**monoBERT** (Pointwise): Each document is scored independently. Concatenate query and doc with [SEP], predict relevance score.

**duoBERT** (Pairwise): Extends monoBERT by comparing pairs - "Given query Q, is document A more relevant than B?" Typically used as a second stage after monoBERT to resolve fine-grained distinctions.

**ListBERT/ListT5** (Listwise): Consider the full list of documents simultaneously using listwise loss functions (ListMLE, Softmax Cross Entropy). [ListT5](https://arxiv.org/abs/2402.15838) uses Fusion-in-Decoder architecture and achieves state-of-the-art zero-shot retrieval.

### ColBERT: Late Interaction for Fine-Grained Matching

[ColBERT](https://arxiv.org/abs/2004.12832) (Contextualized Late Interaction over BERT) offers a compelling middle ground between bi-encoders and cross-encoders.

#### The Late Interaction Paradigm

Unlike cross-encoders that process query+doc together, ColBERT uses **late interaction**:

```
┌─────────────────────────────────────────────────────────────────┐
│                    COLBERT ARCHITECTURE                          │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  Query: "sweet apple"          Document: "The apple is crisp"   │
│         ↓                                    ↓                   │
│  ┌─────────────────┐           ┌─────────────────────────────┐  │
│  │ BERT Encoder    │           │ BERT Encoder (precomputed)  │  │
│  └─────────────────┘           └─────────────────────────────┘  │
│         ↓                                    ↓                   │
│  Token embeddings:              Token embeddings:               │
│  [v_sweet, v_apple]             [v_The, v_apple, v_is, v_crisp] │
│         │                                    │                   │
│         └──────────── MaxSim ────────────────┘                  │
│                         ↓                                        │
│                   Relevance Score                                │
│                                                                  │
└─────────────────────────────────────────────────────────────────┘
```

#### MaxSim: The Scoring Mechanism

MaxSim computes the maximum similarity between each query token and ALL document tokens:

$$\text{Score}(q, d) = \sum_{i=1}^{|q|} \max_{j=1}^{|d|} \cos(q_i, d_j)$$

```python
import numpy as np

def maxsim_score(query_vectors: np.ndarray, doc_vectors: np.ndarray) -> float:
    """
    ColBERT MaxSim scoring.

    Args:
        query_vectors: Shape (num_query_tokens, embedding_dim)
        doc_vectors: Shape (num_doc_tokens, embedding_dim)

    Returns:
        Relevance score (sum of max similarities)
    """
    # Compute all pairwise similarities at once
    # Shape: (num_query_tokens, num_doc_tokens)
    similarities = np.dot(query_vectors, doc_vectors.T)

    # Normalize for cosine similarity
    q_norms = np.linalg.norm(query_vectors, axis=1, keepdims=True)
    d_norms = np.linalg.norm(doc_vectors, axis=1, keepdims=True)
    similarities = similarities / (q_norms @ d_norms.T + 1e-8)

    # MaxSim: for each query token, take max over all doc tokens
    max_sims = similarities.max(axis=1)

    return float(max_sims.sum())


# Example
query = "sweet apple"  # → 2 token embeddings
doc = "The apple is sweet and crisp"  # → 6 token embeddings

# "sweet" matches "sweet" in doc → high max sim
# "apple" matches "apple" in doc → high max sim
# Result: high relevance score
```

#### Why MaxSim Works

Consider query "sweet apple" and two documents:

- **Doc 1**: "The apple is sweet and crisp" → High MaxSim (both tokens match)
- **Doc 2**: "The banana is yellow" → Low MaxSim (neither token matches well)

This **token-level matching** captures fine-grained relevance that bi-encoders miss.

#### ColBERT vs Cross-Encoder Trade-offs

| Aspect             | Cross-Encoder              | ColBERT                      |
| ------------------ | -------------------------- | ---------------------------- |
| **Accuracy**       | Slightly higher            | Very close                   |
| **Latency**        | ~100-300ms/query           | ~50-100ms/query              |
| **Precomputation** | None (recompute each time) | Doc embeddings precomputed   |
| **Storage**        | Minimal                    | Heavy (all token embeddings) |

#### Storage Considerations

ColBERT's main drawback is storage. For each document:

- Standard embedding: 1 vector (768 dims × 4 bytes = 3KB)
- ColBERT: ~128 vectors (128 tokens × 128 dims × 4 bytes = **64KB per doc**)

For 100,000 documents: **~6.4 GB** just for ColBERT embeddings.

#### When to Use ColBERT

✅ **Good fit:**

- Large corpus with speed requirements
- Queries benefit from fine-grained token matching
- You have storage budget for token embeddings

❌ **Not ideal:**

- Storage is constrained
- Simple queries (bi-encoder sufficient)
- Very few documents (cross-encoder is fast enough)

#### ColBERT v2 and ColPali

**[ColBERTv2](https://arxiv.org/abs/2112.01488)**: Adds compression to reduce storage by 6-10x while maintaining quality.

**[ColPali](https://arxiv.org/abs/2407.01449)**: Extends late interaction to **multimodal retrieval**, processing PDF screenshots directly instead of OCR text.

### LLM reranking (listwise)

For the hardest queries, use an LLM to reason about relevance:

```python
def llm_rerank(query: str, candidates: List[str], top_k: int = 5) -> List[str]:
    """Use LLM to rerank candidates."""
    prompt = f"""Given the query and documents, rank them by relevance.

Query: {query}

Documents:
{chr(10).join(f'[{i}] {doc}' for i, doc in enumerate(candidates))}

Return the document numbers in order of relevance (most relevant first).
Format: [3], [1], [5], ...
"""
    response = llm.generate(prompt)
    # Parse the ranking from response
    return parse_ranking(response, candidates)[:top_k]
```

<Callout title="Warning" variant="warning">
  LLM reranking is expensive and slow. Use only when: (1) queries are hard, (2)
  volume is low, (3) stakes are high.
</Callout>

### Reranking cascade

For latency-sensitive systems, use a cascade:

```python
def cascade_rerank(query: str, candidates: List[str]) -> List[str]:
    """
    Cascade: cheap shortlist → expensive rerank.
    """
    # Stage 1: Fast reranker on all candidates (e.g., MiniLM)
    shortlist = fast_reranker.rerank(query, candidates, top_k=20)

    # Stage 2: Expensive reranker on shortlist (e.g., large cross-encoder)
    final = expensive_reranker.rerank(query, shortlist, top_k=5)

    return final
```

## Failure modes

1. **Reranking too few candidates**: Rerank at least 20-50. If you only rerank top-5, you might miss the best result.
2. **Reranking too many**: Diminishing returns + latency. 50-100 is usually enough.
3. **Model mismatch**: Use rerankers trained on similar domains (MS MARCO for general, domain-specific for specialized).
4. **Ignoring diversity**: Reranking by relevance alone can create redundant results. Consider MMR.

## Production defaults

- **Default**: Cross-encoder rerank top-50 → keep top-5/10.
- **Budget**: MS MARCO MiniLM (fast, good quality).
- **Quality**: Cohere Rerank or larger cross-encoders.
- **Hard queries**: LLM rerank as fallback, not default.
