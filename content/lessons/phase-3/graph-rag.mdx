## Core idea

Traditional RAG finds documents. **Graph RAG finds connections.** This approach excels when you need to understand relationships across your entire corpus, not just semantic similarity.

### The Three Problems Graph RAG Solves

#### Problem 1: Multi-Hop Reasoning

**Question:** "Which projects are at risk based on team member dependencies?"
**Graph RAG** Traces: `Team A → depends on → Person X → also on → Project Y → behind schedule`

#### Problem 2: Thematic Synthesis

**Question:** "What are the recurring themes in our research?"
**Graph RAG** Identifies **concept clusters** (communities) across ALL documents.

#### Problem 3: Relationship Discovery

**Question:** "How are these two topics connected?"
**Graph RAG** Explains the path: "Topic A connects to Topic B through concepts X, Y, and Z."

### When to use Graph RAG

- ✅ Multi-document synthesis needed
- ✅ Relationship mapping matters
- ✅ "How do these connect?" questions

### When to stick with Traditional RAG

- ⚡ Simple similarity search
- ⚡ Speed is critical (< 100ms latency)
- ⚡ "Find documents about X" questions

## Implementation Deep Dive

### Step 1: Entity Extraction

The foundation of Graph RAG is extracting **entities** and **relationships** from your documents.

```python
def extract_entities_and_relations(document: str) -> list[dict]:
    """
    Use an LLM to extract (subject, predicate, object) triples.
    """
    prompt = f"""
    Extract all entities and their relationships from this text.
    Format each as: (SUBJECT, PREDICATE, OBJECT)

    Example:
    Text: "Alice works at OpenAI on the GPT project."
    Output:
    - (Alice, works_at, OpenAI)
    - (Alice, works_on, GPT project)
    - (GPT project, belongs_to, OpenAI)

    Text: {document}
    """
    return llm.extract_triples(prompt)
```

### Step 2: Knowledge Graph Construction

Build a graph data structure from the extracted triples:

```python
import networkx as nx

def build_knowledge_graph(triples: list[tuple]) -> nx.Graph:
    """
    Construct a knowledge graph from entity-relation triples.
    """
    G = nx.Graph()

    for subject, predicate, obj in triples:
        # Add nodes with metadata
        G.add_node(subject, type="entity")
        G.add_node(obj, type="entity")

        # Add edge with relationship type
        G.add_edge(subject, obj, relation=predicate)

    return G
```

### Step 3: Community Detection

Group related entities into communities using the Leiden algorithm:

```python
from cdlib import algorithms

def detect_communities(graph: nx.Graph) -> list[list[str]]:
    """
    Find communities of densely connected entities.
    """
    communities = algorithms.leiden(graph)
    return communities.communities
```

### Step 4: Community Summarization

Generate natural language summaries for each community:

```python
def summarize_community(community: list[str], graph: nx.Graph) -> str:
    """
    Create a coherent summary of what this community represents.
    """
    # Extract all edges within the community
    subgraph = graph.subgraph(community)
    edges = list(subgraph.edges(data=True))

    prompt = f"""
    These entities are densely connected: {community}
    Their relationships: {edges}

    Write a 2-3 sentence summary of what this community represents.
    """
    return llm.summarize(prompt)
```

### Step 5: Graph-Augmented Retrieval

When a query comes in, use the graph for enhanced retrieval:

```python
def graph_rag_retrieve(query: str, graph: nx.Graph, summaries: dict) -> list[str]:
    """
    Graph-augmented retrieval with multi-hop reasoning.
    """
    # 1. Entity linking: Find entities mentioned in query
    query_entities = extract_entities(query)

    # 2. Graph traversal: Find connected entities (1-2 hops)
    related_entities = set()
    for entity in query_entities:
        if entity in graph:
            neighbors = nx.single_source_shortest_path_length(graph, entity, cutoff=2)
            related_entities.update(neighbors.keys())

    # 3. Community context: Get relevant community summaries
    relevant_communities = []
    for entity in related_entities:
        community = get_community_for_entity(entity)
        if community:
            relevant_communities.append(summaries[community])

    # 4. Combine with traditional retrieval
    vector_results = traditional_rag_search(query)

    return {
        "graph_context": relevant_communities,
        "vector_context": vector_results,
        "reasoning_path": list(related_entities)
    }
```

## Production defaults

### When to deploy

Graph RAG is expensive. Use it for offline analysis or high-value queries where 5-10s latency is acceptable.

### Performance vs Traditional RAG

| Metric                   | Traditional RAG | Graph RAG   |
| :----------------------- | :-------------- | :---------- |
| **Latency**              | 50-200ms        | 500-2000ms+ |
| **Accuracy (Multi-hop)** | ~30%            | ~75%        |
| **Cost**                 | Low             | Medium-High |

### Recommended Settings

- **Community Detection**: Leiden algorithm (resolution 1.0)
- **Summaries**: Abstractive, 50-100 words per community
- **Graph Pruning**: Remove nodes with degree < 2 to reduce noise

## Failure modes

### 1. The "Everything Connects" Trap

If your graph is too dense, everything connects to everything. The retrieval becomes noisy and expensive. **Fix:** Be specific in your extraction prompt about WHICH relationships matter.

### 2. Entity Duplication

"OpenAI", "Open AI", and "OPENAI" appearing as different nodes. **Fix:** Run entity resolution (deduplication) before graph construction.

### 3. Missing Thematic Synthesis

Building a graph without _community summaries_ misses the "forest for the trees". **Fix:** Ensure step 4 (summarization) is robust.
