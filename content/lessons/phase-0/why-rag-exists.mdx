- Learn the mental model: **parametric vs non‑parametric memory**.
- Know what you should build first (and what to ignore early).

## Core idea

RAG = **Retrieve** relevant context from your documents, then **Generate** an answer using that context.

### The problem RAG solves

Large Language Models (LLMs) can:

- Write fluent text
- Generalize across tasks
- Reason *sometimes*

But they also:

- **Hallucinate** (confidently produce incorrect details)
- Have **stale knowledge** (their training cutoff)
- Can't reliably access your **private / fresh** data

### The core architecture: parametric vs non-parametric memory

LLMs are **parametric memory** systems: they compress knowledge into fixed weights.

- **Knowledge cutoff**: training data becomes stale.
- **Hallucination**: fluent text ≠ truth.
- **Privacy**: your internal data isn’t accessible unless you provide it.

RAG adds **non‑parametric memory**: an external store you can update, permission, and debug.

### Minimal pipeline

1. **Chunk** documents
2. **Embed** chunks into vectors
3. **Retrieve** top-k chunks for a query
4. **Prompt** the LLM with the retrieved context

### Offline vs online (production reality)

In production you separate **offline indexing** from **online query time**.

- **Offline**: parse → chunk → metadata → embed → store
- **Online**: query → retrieve candidates → rerank → shape context → generate + cite/refuse

## Failure modes

- **Prompt-first debugging**: trying to “prompt your way out” when the right evidence isn’t retrieved.
- **Vectors-only retrieval**: missing exact terms (IDs, acronyms) that BM25/hybrid would catch.
- **Over-retrieval**: k too high → context rot → the model ignores key evidence.

## Production defaults

- Start with **hybrid retrieval + reranking** as your production baseline.
- Keep contexts small: retrieve 20–50 → rerank → keep 5–10 → cite everything.
