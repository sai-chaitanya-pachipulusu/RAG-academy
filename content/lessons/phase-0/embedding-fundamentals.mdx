## Goals

- Build the correct intuition for “meaning as geometry”.
- Understand why similarity math matters, but isn’t the main bottleneck.
- Be ready to implement the primitives used by vector databases.

## Core idea

### What is an embedding?

An **embedding** maps content (text, image, code) into a vector of numbers:

- similar meaning → vectors are close
- different meaning → vectors are far

This turns “search for meaning” into a geometry problem.

### Similarity vs distance

You’ll see both in practice:

- **Cosine similarity** (most common for embeddings)
- **Dot product** (often used directly, especially if vectors are normalized)
- **Euclidean distance** (good for intuition; less common for modern text embeddings)

<Callout title="Key idea" variant="success">
  Retrieval quality often depends more on chunking + query formulation than the exact similarity metric.
</Callout>

## Failure modes

- **Vectors-only retrieval**: you will miss exact terms (IDs/acronyms) unless you use hybrid retrieval.
- **Model mismatch**: query and docs embedded with different models → similarity becomes meaningless.
- **Wrong chunking**: embeddings can’t recover lost structure (garbage in → garbage out).

## Production defaults

- Choose one good baseline embedding model and evaluate changes with Recall@k.
- Prefer **hybrid + reranking** improvements before fine-tuning embeddings.
- Use Compare when choosing models:
