## Goals

- Understand why chunking exists (and why it’s so often the root cause).
- Learn two baseline chunking strategies you can ship.
- Learn how to spot “bad chunking” in logs when retrieval fails.

## Prereqs

- Read: **Tokenizers & Context Windows** (token budgets drive chunk size decisions).

## Core idea

### Why chunking matters

In RAG you don’t retrieve entire documents—you retrieve **chunks**.

Good chunking:

- keeps semantic units together
- stays within token budgets
- makes retrieval precise

Bad chunking:

- splits definitions from the thing they define
- mixes multiple topics
- causes “almost relevant” context that confuses the model

### Two simple strategies

1. **Fixed-size chunking**: easiest to implement, often “good enough” to start.
2. **Overlap**: reduces boundary loss (but increases index size).

## Failure modes

- **Too small**: definitions split from what they define → fragments get retrieved.
- **Too large**: irrelevant text dilutes relevance → context rot + token waste.
- **Wrong boundaries**: splitting in the middle of a table, list, or code block.
- **No traceability**: missing chunk IDs / source mapping → impossible to debug.

## Production defaults

- Start with **300–600 tokens** per chunk, **10–20% overlap**.
- Prefer structure-aware splitting when you have headings (Markdown/PDF sections).
- Always store: `doc_id`, stable `chunk_id`, section/page metadata.
