<Callout title="Goal" variant="info">
  Implement the production reranking pattern: **retrieve a shortlist → rerank with an expensive model → keep the final top‑k**.
</Callout>

## Why this matters in production

Dense/BM25 retrieval is optimized for **speed and recall**, not perfect ranking.

Cross-encoders (or hosted rerank APIs) are optimized for **precision**, but they’re expensive:

- they score **query + doc together**
- cost scales with number of candidates

So production does this:

1. retrieve top‑N fast (often 20–50)
2. rerank top‑N with cross‑encoder
3. keep top‑k (often 5–10) for context

## What this challenge enforces

The tests track how many times the “expensive” `cross_encoder_score()` runs.

If you rerank every document, you fail the spirit (and the test).

## How this maps to real systems

- `cheap_score` ≈ dense/BM25 retrieval
- `cross_encoder_score` ≈ Cohere Rerank / bge-reranker / LLM reranker
- `k_initial` ≈ candidate pool size
- `k_final` ≈ context size
