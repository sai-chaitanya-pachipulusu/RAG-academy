## Why Embedding Cache Keys Matter in Production

Embedding caching can reduce API costs by 50%+ for repetitive content. The key is normalizing inputs so semantically equivalent texts hit the cache. Without proper normalization:

- "Machine Learning" and "machine learning" cache separately
- "  spaced text  " and "spaced text" cache separately
- "The quick brown fox" and "quick brown fox" might cache separately

### Real-World Scenario

A RAG system processing user queries:

- Query 1: "What is machine learning?"
- Query 2: "what is Machine Learning?"
- Query 3: "What is machine learning?  "

All three are semantically identical. With proper cache key generation:
- All three generate the same cache key
- Only one API call made
- 66% cost savings on these queries

## The Mathematical Foundation

### Cache Key Generation Pipeline

```
Raw Text → Normalize → Hash (if long) → Cache Key
```

### Normalization Steps

| Step | Input | Output | Purpose |
|------|-------|--------|---------|
| **Lowercase** | "Hello World" | "hello world" | Case insensitivity |
| **Whitespace collapse** | "a  b\t\nc" | "a b c" | Formatting independence |
| **Trim** | "  text  " | "text" | Leading/trailing spaces |
| **Unicode normalize** | "café" | "cafe" (NFD) | Character equivalence |

### Hashing Strategy

For long texts, hash to fixed-length key:

```
if (normalizedText.length > maxKeyLength) {
  key = hash(normalizedText); // SHA-256, etc.
} else {
  key = normalizedText;
}
```

Trade-off: Hashing prevents key size explosion but introduces collision risk (extremely low with SHA-256).

### Model-Aware Keys

Different models produce different embeddings for same text:

```
cacheKey = modelName + ":" + normalizedTextHash
```

Examples:
- `text-embedding-3-small:abc123...`
- `text-embedding-ada-002:abc123...`

## Theoretical Deep Dive

### Cache Hit Rate Optimization

Factors affecting hit rate:

```
Hit Rate = f(normalization_aggressiveness, text_diversity, query_patterns)
```

More aggressive normalization → Higher hit rate but risk of false positives

### Collision Probability

For SHA-256 (256 bits):

```
Probability of collision with n keys ≈ n² / (2 × 2²⁵⁶)

For 1 billion keys: P(collision) ≈ 10⁻⁶⁰ (effectively zero)
```

### Semantic Equivalence Classes

Normalization defines equivalence classes:

```
["ML", "ml", "Ml", "mL"] → equivalence class → same cache key
["Machine Learning", "machine learning"] → same equivalence class
```

## Production Considerations

### Incremental Normalization

For streaming/chunked text:

```typescript
class IncrementalNormalizer {
  private buffer: string = '';
  
  add(text: string): void {
    this.buffer += text;
  }
  
  finalize(): string {
    return normalize(this.buffer);
  }
}
```

### Multi-Tenant Isolation

Prevent cache poisoning across users:

```
cacheKey = tenantId + ":" + modelName + ":" + normalizedTextHash
```

### Cache Warming

Pre-populate cache for common queries:

```typescript
const commonQueries = [
  "what is rag",
  "how does semantic search work",
  // ...
];

for (const query of commonQueries) {
  const key = generateCacheKey(query, model);
  const embedding = await getEmbedding(query);
  await cache.set(key, embedding);
}
```

### Validation Checklist

- [ ] Case normalization: "ABC" and "abc" produce same key
- [ ] Whitespace collapse: "a  b" and "a b" produce same key
- [ ] Trim: " text " and "text" produce same key
- [ ] Model prefix included when configured
- [ ] Long texts hashed correctly
- [ ] Empty text handled gracefully
- [ ] Unicode normalized (é → e in NFD)

## Common Pitfalls

- **Not normalizing**: Missing cache hits from trivial differences
- **Hash collisions for very different texts**: Use strong hash (SHA-256)
- **Not including model name**: Different models → different embeddings
- **Over-normalization**: Removing meaningful differences
- **Unicode issues**: Different normalization forms (NFC vs NFD)
