## Why Top-K Search Matters in Production

Top-k search is what every vector database does: find the k most similar documents to a query. This exact pattern runs millions of times per day at Pinecone, Weaviate, and Qdrant. Understanding top-k search is fundamental to:

- **RAG retrieval**: Finding relevant context
- **Recommendation**: Similar item discovery
- **Clustering**: Finding nearest neighbors
- **Classification**: K-nearest neighbors

### Real-World Scenario

A RAG system with 1M documents:

```
Query: "machine learning tutorials"
Query embedding: [0.1, -0.3, 0.5, ...] (1536 dimensions)

Top-k search:
1. Compute similarity with all 1M documents
2. Keep track of top 10 highest scores
3. Return: [doc_4521, doc_8912, doc_1234, ...]

Time: O(n × d) where n=1M, d=1536
With optimization: Can be O(log n) with indexing
```

## The Mathematical Foundation

### Top-K Algorithm

```
Input: query vector q, document vectors D, integer k
Output: k documents with highest similarity to q

Algorithm:
1. Initialize min-heap of size k
2. For each document d in D:
   a. Compute similarity(q, d)
   b. If heap not full: add to heap
   c. Else if similarity > heap.min: replace min
3. Return heap contents sorted by similarity
```

### Complexity Analysis

| Operation | Complexity | Explanation |
|-----------|-----------|-------------|
| **Similarity computation** | O(d) | d = dimensions |
| **Full scan** | O(n × d) | n = documents |
| **With min-heap** | O(n × log k) | Heap operations |
| **With indexing** | O(log n) | HNSW, IVF, etc. |

### Similarity Metrics

| Metric | Formula | Best For |
|--------|---------|----------|
| **Cosine** | (a·b) / (\|a\| \|b\|) | Text embeddings |
| **Dot Product** | a·b | Normalized vectors |
| **Euclidean** | \|a - b\| | Distance matters |

## Theoretical Deep Dive

### Exact vs Approximate Search

| Type | Guarantee | Speed | Use Case |
|------|-----------|-------|----------|
| **Exact** | 100% accurate | Slower | Small datasets, critical apps |
| **Approximate** | >95% recall | 10-100x faster | Large datasets, real-time |

### Index Structures

| Index | Query Time | Build Time | Best For |
|-------|-----------|------------|----------|
| **Flat** | O(n) | O(1) | Small datasets (<10K) |
| **IVF** | O(√n) | O(n) | Medium datasets |
| **HNSW** | O(log n) | O(n log n) | Large datasets |
| **LSH** | O(1) | O(n) | Very large, approximate |

### The Curse of Dimensionality

```
In high dimensions (d > 100):
- Distances become more uniform
- Relative contrast decreases
- Indexing becomes harder

Solution: Use dimensionality reduction or specialized indices
```

## Production Considerations

### Batch Queries

Process multiple queries efficiently:

```typescript
async function batchTopKSearch(
  queries: number[][],
  documents: number[][],
  k: number
): Promise<Array<Array<{ id: string; score: number }>>> {
  return Promise.all(
    queries.map(q => topKSearch(q, documents, k))
  );
}
```

### Filtering

Combine with metadata filters:

```typescript
function filteredTopKSearch(
  query: number[],
  documents: Document[],
  filter: (doc: Document) => boolean,
  k: number
): Result[] {
  const filtered = documents.filter(filter);
  return topKSearch(query, filtered, k);
}
```

### Validation Checklist

- [ ] k results returned (or all if fewer)
- [ ] Results sorted by score descending
- [ ] Correct similarity metric used

- [ ] Ranks assigned correctly (1-indexed)
- [ ] Timing measured

## Common Pitfalls

- **Sorting in wrong order**: Should be descending (highest first)
- **Not handling `k > documents.length`**: Return all available
- **Using wrong similarity metric**: Cosine vs dot vs Euclidean
- **Not validating dimensions**: Mismatched vectors cause errors
- **Inefficient for large k**: Use min-heap, not full sort
