## Why Recall@K Matters in Production

Recall@K answers: "Of all relevant documents, what fraction did we retrieve in the top K?" It's the primary metric for RAG because if you don't retrieve relevant context, the LLM can't use it. Without good recall:

- LLM lacks information to answer accurately
- Hallucinations increase due to missing context
- User trust decreases
- System fails its primary purpose

### Real-World Scenario

For a query about "machine learning benefits":

**Ground truth relevant documents:** [doc_A, doc_B, doc_C, doc_D] (4 total)

**Retrieved top-5:** [doc_X, doc_A, doc_Y, doc_B, doc_Z]

**Analysis:**
- Relevant retrieved: doc_A, doc_B (2 documents)
- Total relevant: 4 documents
- Recall@5 = 2/4 = 0.5

Interpretation: We found 50% of relevant documents in top-5.

## The Mathematical Foundation

### Recall@K Formula

$$\text{Recall}@K = \frac{|\{\text{Relevant documents}\} \cap \{\text{Top-K retrieved}\}|}{|\{\text{Relevant documents}\}|}$$

Or simply:

$$\text{Recall}@K = \frac{\text{Relevant retrieved}}{\text{Total relevant}}$$

### Example Calculations

| K | Retrieved | Relevant | Relevant in Top-K | Recall@K |
|---|-----------|----------|-------------------|----------|
| 1 | [A, B, C] | [A, D] | [A] | 1/2 = 0.5 |
| 3 | [A, B, C] | [A, D] | [A] | 1/2 = 0.5 |
| 5 | [A, B, C, D, E] | [A, D] | [A, D] | 2/2 = 1.0 |

### Properties

| Property | Description |
|----------|-------------|
| **Range** | [0, 1] where 1 = perfect recall |
| **Monotonic** | Recall@K+1 ≥ Recall@K |
| **Position independent** | Only cares about presence, not rank |
| **Binary relevance** | Document is relevant or not |

## Theoretical Deep Dive

### Recall vs Precision

| Metric | Question | Focus |
|--------|----------|-------|
| **Recall@K** | "Did we find relevant items?" | Coverage |
| **Precision@K** | "Are retrieved items relevant?" | Accuracy |

For RAG, recall is typically more important because:
- LLM can filter out irrelevant context
- LLM cannot invent missing context

### The Recall-Precision Trade-off

```
Higher K → Higher recall, Lower precision
Lower K → Lower recall, Higher precision

Optimal K balances:
- Enough context for LLM
- Not overwhelming with noise
```

### Multi-Query Aggregation

Across multiple queries:

$$\text{Mean Recall}@K = \frac{1}{|Q|} \sum_{i=1}^{|Q|} \text{Recall}_i@K$$

Or macro-average by averaging per-query recall.

## Production Considerations

### Choosing K

Common values for RAG:

| K | Use Case | Trade-off |
|---|----------|-----------|
| 3-5 | Concise answers | May miss relevant context |
| 10 | Balanced | Good coverage, manageable noise |
| 20-50 | Comprehensive research | High coverage, more filtering needed |
| 100 | Maximum recall | Use with reranking |

### Recall@K vs MRR

| Scenario | Use Recall@K | Use MRR |
|----------|--------------|---------|
| Multiple relevant docs | ✓ | ✗ |
| Single best answer needed | ✗ | ✓ |
| Need coverage metric | ✓ | ✗ |
| Need ranking quality | ✗ | ✓ |

### Statistical Significance

```typescript
function bootstrapRecall(
  results: QueryResult[],
  k: number,
  iterations: number = 1000
): { mean: number; ci95: [number, number] } {
  const samples = [];
  for (let i = 0; i < iterations; i++) {
    const sample = resample(results);
    samples.push(calculateMeanRecall(sample, k));
  }
  return {
    mean: mean(samples),
    ci95: [percentile(samples, 0.025), percentile(samples, 0.975)]
  };
}
```

### Validation Checklist

- [ ] All relevant in top-K → recall = 1.0
- [ ] No relevant in top-K → recall = 0.0
- [ ] Half relevant in top-K → recall = 0.5
- [ ] k > length uses all documents
- [ ] k <= 0 returns 0
- [ ] Empty relevant set handled (return 0 or throw)
- [ ] Duplicate doc IDs handled correctly
- [ ] Multiple queries averaged correctly

## Common Pitfalls

- **Dividing by retrieved count instead of relevant count**: That's precision, not recall
- **Not handling empty relevant set**: Division by zero
- **Using 0-indexed K**: Recall@1 should check first document only
- **Counting duplicates**: Ensure unique document counting
