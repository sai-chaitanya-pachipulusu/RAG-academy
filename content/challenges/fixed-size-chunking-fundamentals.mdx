## Why this matters in production

Chunking quality dominates retrieval quality for most RAG systems.

Even if you later use:

- header-aware chunking
- semantic chunking
- proposition chunking

…you still need a rock-solid baseline to compare against.

## What you're implementing

- Split raw text into contiguous slices of size `chunk_size`
- Preserve text exactly (no trimming)
- Validate parameters (`chunk_size > 0`)

## When Simple Chunking Wins

Simple chunking is often the best choice when:
- Documents have consistent structure
- You need predictable chunk sizes for cost estimation
- You're building a baseline to compare against fancy chunkers
- Processing speed is critical

## The Algorithm

```python
def fixed_size_chunk(text: str, chunk_size: int) -> list[str]:
    """
    Split text into fixed-size chunks.
    
    Time Complexity: O(N) where N = len(text)
    Space Complexity: O(N) for output chunks
    
    Args:
        text: Input text to chunk
        chunk_size: Size of each chunk in characters
        
    Returns:
        List of chunks, each with length <= chunk_size
        
    Raises:
        ValueError: If chunk_size <= 0
    """
    if chunk_size <= 0:
        raise ValueError("chunk_size must be positive")
    
    chunks = []
    for i in range(0, len(text), chunk_size):
        chunks.append(text[i:i + chunk_size])
    
    return chunks
```

## Complexity Analysis

| Aspect | Complexity | Notes |
|--------|------------|-------|
| Time | O(N) | Single pass through text |
| Space | O(N) | Output storage |
| Memory | O(chunk_size) | Working buffer |

## Common pitfalls

- Off-by-one errors at the end of the string.
- Accidentally trimming whitespace (this changes hashes/traceability later).
- Not validating `chunk_size > 0` (infinite loops or crashes).
