## The Performance Problem

In production RAG, you don't compare one query against one document — you compare **one query against thousands or millions** of documents simultaneously.

### Performance Comparison

| Approach | Time for 1M vectors | Relative Speed |
|----------|---------------------|----------------|
| Naive Python loop | ~10 seconds | 1x (baseline) |
| Vectorized NumPy | ~50 milliseconds | 200x faster |
| FAISS (CPU) | ~5 milliseconds | 2000x faster |
| FAISS (GPU) | ~0.5 milliseconds | 20000x faster |

**Key insight**: The mental model you build here translates directly to understanding FAISS, HNSW, and other ANN libraries.

## Theoretical Foundation

### Matrix-Vector Multiplication

Given:
- Query vector **q** ∈ ℝᵈ (1 × d)
- Document matrix **D** ∈ ℝⁿˣᵈ (n documents, d dimensions)

The scores are computed as:

$$\text{scores} = D \cdot q^T$$

Result: Vector of n similarity scores.

### Computational Complexity

| Operation | Time Complexity | Space Complexity |
|-----------|-----------------|------------------|
| Single dot product | O(d) | O(1) |
| Batched (n vectors) | O(n × d) | O(n) for results |
| With matrix multiply | O(n × d) | O(n) for results |

**Note**: While asymptotic complexity is the same, constant factors differ dramatically due to:
- CPU cache efficiency
- SIMD instructions (AVX, SSE)
- Memory bandwidth utilization
- GPU parallelization

### Memory Layout Matters

```python
# Row-major (C-style): Documents stored row-by-row
# Better for iterating over documents
docs = [[d1_dim1, d1_dim2, ...],
        [d2_dim1, d2_dim2, ...],
        ...]

# Column-major (Fortran-style): Dimensions stored together  
# Better for SIMD operations
docs_T = [[d1_dim1, d2_dim1, ...],
          [d1_dim2, d2_dim2, ...],
          ...]
```

Modern libraries (NumPy, PyTorch) handle this automatically, but understanding it helps debug performance issues.

## Production Implementations

### NumPy Vectorization

```python
import numpy as np

# Query: (d,) array
# Docs: (n, d) matrix
# Result: (n,) array of scores

def batch_dot_numpy(query: np.ndarray, docs: np.ndarray) -> np.ndarray:
    """
    Vectorized batch dot product.
    Uses BLAS under the hood for optimal performance.
    """
    return docs @ query  # Matrix-vector multiply
```

### PyTorch (GPU Acceleration)

```python
import torch

def batch_dot_torch(query: torch.Tensor, docs: torch.Tensor) -> torch.Tensor:
    """
    GPU-accelerated batch dot product.
    Moves computation to GPU if available.
    """
    device = torch.device('cuda' if torch.cuda.is_available() else 'cpu')
    query = query.to(device)
    docs = docs.to(device)
    return torch.matmul(docs, query)
```

### Pure Python (Educational)

```python
def batch_dot_python(query: list, docs: list[list]) -> list[float]:
    """
    Pure Python implementation.
    ~100x slower than NumPy but illustrates the algorithm.
    """
    return [sum(q * d for q, d in zip(query, doc)) for doc in docs]
```

## Scaling to Millions: The ANN Transition

### Exact Search Limitations

| Dataset Size | Exact Search Time | Acceptable? |
|--------------|-------------------|-------------|
| 10K vectors | 1 ms | ✅ Yes |
| 100K vectors | 10 ms | ✅ Yes |
| 1M vectors | 100 ms | ⚠️ Marginal |
| 10M vectors | 1 second | ❌ No |
| 100M vectors | 10 seconds | ❌ No |

### Approximate Nearest Neighbor (ANN)

When exact search is too slow, ANN algorithms trade a small accuracy loss for massive speed gains:

| Algorithm | Recall@10 | 1M vectors | 100M vectors |
|-----------|-----------|------------|--------------|
| Exact | 100% | 100 ms | 10 s |
| HNSW | 95% | 1 ms | 5 ms |
| IVF | 90% | 2 ms | 10 ms |
| LSH | 85% | 5 ms | 50 ms |
