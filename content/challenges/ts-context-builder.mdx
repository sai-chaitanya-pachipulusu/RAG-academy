## Why Context Building Matters in Production

Context window management directly impacts RAG quality. The "lost in the middle" paper showed that LLMs pay less attention to middle context — ordering matters! Poor context building leads to:

- **Truncated responses**: Not reserving enough tokens for answers
- **Lost information**: Important chunks in the middle get ignored
- **Token waste**: Inefficient packing leaves context window underutilized
- **Hallucinations**: LLM invents information when context is missing

### Real-World Scenario

A customer support RAG system with 8K context limit:

- **Poor context building**:
  - Fill entire 8K with retrieved chunks
  - No room for LLM response → truncated answers
  - Random chunk order → important info in middle

- **Optimal context building**:
  - Reserve 2K tokens for response
  - Pack 5K tokens of most relevant chunks
  - Leave 1K buffer for system prompt
  - Order: best chunks at start and end

## The Mathematical Foundation

### Token Budget Allocation

```
Total Context = System Prompt + Context Chunks + Query + Response Buffer

Example (8K context):
- System prompt: 500 tokens
- Context chunks: 5,500 tokens (the variable part)
- Query: 200 tokens
- Response buffer: 1,500 tokens
- Safety margin: 300 tokens
Total: 8,000 tokens
```

### The "Lost in the Middle" Effect

Research shows LLM attention follows a U-curve:

```
Attention Score
    ▲
  1 │ ╭─╮                           ╭─╮
    │╭╯ ╰╮                         ╭╯ ╰╮
  0.5│    ╰╮                       ╭╯    ╰╮
    │      ╰─────────────────────╯        ╰
  0 └────────────────────────────────────────► Position
    Start                              End
```

**Implication**: Place most important information at the beginning and end of context.

### Ordering Strategies

| Strategy | Algorithm | Best For |
|----------|-----------|----------|
| **Relevance** | Sort by score descending | Standard RAG |
| **Lost-in-middle** | Best, worst, 2nd best, 2nd worst... | Long contexts |
| **Chronological** | By timestamp | News, updates |
| **Document order** | Original document position | Narratives |

## Theoretical Deep Dive

### Optimal Chunk Selection

Given:
- Token budget: B
- Chunks: C₁, C₂, ..., Cₙ with sizes s₁, s₂, ..., sₙ and scores r₁, r₂, ..., rₙ

Find subset S that maximizes:
```
Σ rᵢ for i in S
Subject to: Σ sᵢ for i in S ≤ B
```

This is the **0/1 Knapsack Problem** — NP-hard but tractable with dynamic programming for reasonable n.

### Greedy Approximation

For production, greedy selection works well:

```
1. Sort chunks by rᵢ/sᵢ (score per token) descending
2. Add chunks until budget exhausted
3. Time: O(n log n)
```

Achieves at least 50% of optimal score.

### Dynamic Context Sizing

Adjust context based on query complexity:

```typescript
function getContextBudget(query: string): number {
  if (isSimpleQuery(query)) return 2000;
  if (isComplexQuery(query)) return 6000;
  return 4000; // default
}
```

## Production Considerations

### Token Counting Accuracy

Different methods for different precision needs:

| Method | Accuracy | Speed | Use Case |
|--------|----------|-------|----------|
| **Tiktoken** | Exact | Slow | Final check |
| **Character/4** | Estimate | Fast | Initial sizing |
| **Word count** | Rough | Fast | Quick validation |

### Truncation Strategies

When chunks exceed budget:

1. **Drop lowest scoring**: Simple, preserves chunk boundaries
2. **Truncate last chunk**: May lose coherence
3. **Summarize overflow**: Use LLM to compress (expensive)

## Common Pitfalls

- **Forgetting to reserve space for the response**: Causes truncation
- **Not accounting for prompt template tokens**: System prompts add overhead
- **Ignoring "lost in the middle"**: Best chunks buried in middle
- **Over-counting tokens**: Double-counting separators or newlines
- **Not handling oversized single chunks**: May need truncation or rejection
