## The Problem

GDPR's "Right to be Forgotten" means that when a user requests deletion, **all** their data must be removed — including from your vector index.

### Without Source Tracking

1. User requests deletion of "contract_123.pdf"
2. You have 50,000 chunks in your index
3. Which chunks came from that contract? 🤷

**The only option**: Full re-index of all 50,000 chunks — hours of downtime and significant compute cost.

### The Cost of Non-Compliance

| Violation | Fine | Example |
|-----------|------|---------|
| GDPR Article 17 | Up to €20M or 4% revenue | Failure to delete user data |
| CCPA | Up to $7,500 per violation | Unauthorized data retention |
| HIPAA | Up to $1.5M per year | Failure to protect PHI |

## The Solution: Source Fingerprinting

Maintain a bidirectional mapping:

```
source_id → [chunk_ids]  (forward mapping)
chunk_id → source_id     (reverse mapping)
```

### Deletion Workflow

```python
# User requests deletion
chunks_to_delete = tracker.delete_source("contract_123")
# Returns: ["chunk_001", "chunk_002", ..., "chunk_050"]

# Delete from vector database
vector_db.delete(ids=chunks_to_delete)

# Verify deletion
assert tracker.get_chunks_by_source("contract_123") == []
```

**Time complexity**: O(k) where k = chunks per source, not O(n) for full re-index.

## Theoretical Foundation

### Data Lineage

Source fingerprinting is a form of **data lineage tracking**:

```
Original Document
       ↓
   [Parsing]
       ↓
   Chunks
   ├── chunk_1 ← source: doc_123, page: 1
   ├── chunk_2 ← source: doc_123, page: 1
   └── chunk_3 ← source: doc_123, page: 2
```

### Metadata Schema

```python
class ChunkMetadata:
    chunk_id: str           # Unique chunk identifier
    source_id: str          # Document/source identifier
    source_type: str        # "pdf", "webpage", "database", etc.
    created_at: datetime    # When chunk was created
    updated_at: datetime    # When source was last modified
    version: str            # Source version (for updates)
    
    # Optional provenance
    page_number: int        # For PDFs
    url: str                # For web pages
    row_id: str             # For database records
    author: str             # Content creator
```

### Update Scenarios

| Scenario | Action | Implementation |
|----------|--------|----------------|
| **Delete source** | Remove all chunks | `delete_source(source_id)` |
| **Update source** | Replace chunks | `delete_source()` + re-index |
| **Partial update** | Modify specific chunks | Version tracking |
| **Source merge** | Combine sources | Update mappings |

## Production Considerations

### Storage Options

| Storage | Pros | Cons | Best For |
|---------|------|------|----------|
| **In-Memory (dict)** | Fast | Lost on restart | Development |
| **Redis** | Fast, persistent | Extra infra | Production caching |
| **PostgreSQL** | ACID, queryable | Slower | Source of truth |
| **Vector DB metadata** | Colocated | Limited size | Small metadata |

### Distributed Systems

In a distributed RAG system, source tracking must be consistent:

```python
class DistributedSourceTracker:
    def __init__(self, redis_client: redis.Redis):
        self.redis = redis_client
    
    def register_chunk(self, chunk_id: str, source_id: str):
        """Atomic registration using Redis transaction."""
        pipe = self.redis.pipeline()
        pipe.sadd(f"source:{source_id}", chunk_id)
        pipe.hset(f"chunk:{chunk_id}", "source_id", source_id)
        pipe.execute()
    
    def delete_source(self, source_id: str) -> list[str]:
        """Atomic deletion with chunk list return."""
        pipe = self.redis.pipeline()
        pipe.smembers(f"source:{source_id}")
        pipe.delete(f"source:{source_id}")
        chunk_ids = pipe.execute()[0]
        
        # Clean up reverse mappings
        for chunk_id in chunk_ids:
            self.redis.delete(f"chunk:{chunk_id}")
        
        return list(chunk_ids)
```
