 Re-ranker Selection

**Difficulty**: Tier 3 - Advanced Retrieval  
**Prerequisites**: Basic Retrieval, Cross-Encoders, Evaluation Metrics  
**Time Estimate**: 4-5 hours

## Objective

Learn to select and compare reranking models for production RAG systems, understanding the trade-offs between accuracy, latency, and cost.

## Purpose

Reranking transforms decent retrieval results into high-precision answers. The difference between a good and bad reranker choice can be 20-30% improvement in answer relevance. This challenge teaches you to make data-driven reranker decisions.

### Real-World Impact
- **Enterprise search**: 40% improvement in user satisfaction with proper reranker
- **Customer support**: Accurate ranking reduces hallucination by surfacing best context
- **Legal research**: Precision-critical applications require optimized reranking
- **E-commerce**: Product ranking directly impacts conversions

## The Problem

First-stage retrievers (BM25, ANN) are fast but imprecise. Rerankers add a second pass with better accuracy but at higher cost:

**First Stage (Fast, Imprecise)**
- BM25: Lexical matching, CPU-only
- HNSW: Approximate nearest neighbors
- IVF: Inverted file index

**Second Stage (Slow, Precise)**
- Cross-encoders: Full query-doc interaction
- LLM-based: Direct relevance scoring
- ColBERT: Token-level late interaction

**Selection Challenges:**
- Which reranker architecture matches your data?
- How to balance latency vs accuracy?
- Single reranker or cascade?
- When is reranking not worth the cost?

### Reranker Cascade

Use multiple rerankers in stages:

```
Top 100 (Initial Retrieval)
     │
     ▼
┌─────────────────┐  Fast filter
│  MiniLM (22M)   │  → Top 30
└────────┬────────┘
         │
         ▼
┌─────────────────┐  Precise ranking
│ BGE-Reranker    │  → Top 10
│   (560M)        │
└────────┬────────┘
         │
         ▼
   Final Results
```

**Cascade Design Principles:**
1. Each stage reduces candidate pool 3-5x
2. Later stages are slower but more accurate
3. Total latency = sum of all stage latencies

### Challenge 1: Single Reranker Selection

Evaluate each candidate on your test set.

**Acceptance Criteria:**
- Compute nDCG@10 for each reranker
- Measure latency distribution (p50, p95, p99)
- Document accuracy/latency Pareto frontier
- Select optimal model for your constraints

**Evaluation Protocol:**
```python
def evaluate_reranker(reranker, queries, corpus, qrels, k=10):
    """
    Standard evaluation pipeline.
    
    1. Retrieve top 100 with first-stage retriever
    2. Rerank with candidate model
    3. Compute metrics at k
    4. Profile latency
    """
    results = []
    latencies = []
    
    for query in queries:
        start = time.time()
        
        # First stage
        candidates = retriever.search(query, k=100)
        
        # Rerank
        reranked = reranker.rerank(query, candidates)
        
        latencies.append(time.time() - start)
        results.append(reranked[:k])
    
    metrics = {
        'ndcg@10': compute_ndcg(results, qrels),
        'latency_p50': np.percentile(latencies, 50),
        'latency_p99': np.percentile(latencies, 99)
    }
    
    return metrics
```

            # Rerank

            # Extract just the documents for next stage
            current = [doc for doc, _ in reranked]

## Advanced Techniques

### 1. Document Length Normalization

Cross-encoders bias toward longer documents.

```python
def length_normalize_scores(scores: List[float], 
                           doc_lengths: List[int]) -> List[float]:
    """Penalize very long or very short documents."""
    # Pivot at ideal length (e.g., 200 tokens)
    ideal_len = 200
    penalties = [abs(len - ideal_len) / 1000 for len in doc_lengths]
    return [s - p for s, p in zip(scores, penalties)]
```

### 2. Position Bias Correction

Rerankers inherit position bias from first stage.

```python
def position_debiased_rerank(query, candidates, reranker):
    """Shuffle candidates before reranking."""
    import random
    shuffled = candidates.copy()
    random.shuffle(shuffled)
    
    # Rerank twice with different shuffles
    scores1 = reranker.score(query, shuffled)
    random.shuffle(shuffled)
    scores2 = reranker.score(query, shuffled)
    
    # Average to reduce position bias
    return average_scores(scores1, scores2)
```

### 3. Query-Specific Calibration

Adjust scores based on query difficulty:

```python
def calibrate_scores(scores: List[float], 
                    query_difficulty: float) -> List[float]:
    """
    Hard queries: spread scores more (fine-grained discrimination)
    Easy queries: compress scores (clear winners)
    """
    if query_difficulty > 0.7:
        return [s ** 0.5 for s in scores]  # Spread
    else:
        return [s ** 2 for s in scores]    # Compress
```

## Production Tips

### 1. Batch Processing

```python
def batch_rerank(queries: List[str], 
                candidate_lists: List[List[str]], 
                batch_size: int = 32):
    """Process multiple queries together for GPU efficiency."""
    all_pairs = []
    query_indices = []
    
    for i, (query, candidates) in enumerate(zip(queries, candidate_lists)):
        for doc in candidates:
            all_pairs.append((query, doc))
            query_indices.append(i)
            
    # Score all pairs in batches
    scores = model.predict(all_pairs, batch_size=batch_size)
    
    # Reconstruct per-query rankings
    results = [[] for _ in queries]
    for idx, score in zip(query_indices, scores):
        results[idx].append(score)
        
    return results
```

### 2. Early Stopping

```python
def rerank_with_early_stop(query, candidates, reranker, 
                          confidence_threshold: float = 0.9):
    """Stop if top result has very high confidence."""
    top_candidates = candidates[:5]
    scores = reranker.score(query, top_candidates)
    
    if max(scores) > confidence_threshold:
        # High confidence, skip full reranking
        return sorted(zip(top_candidates, scores), key=lambda x: -x[1])
    else:
        # Low confidence, rerank all
        return reranker.rerank(query, candidates)
```

## Summary

Reranker selection is a critical optimization in production RAG. The key trade-off is between accuracy and latency/cost.

**Key Takeaways:**
1. **Benchmark first**: Measure on your data, not just public leaderboards
2. **Start simple**: MiniLM/BGE-base often sufficient
3. **Consider cascade**: 2-stage cascades give 90% of benefit at 50% of cost
4. **Cache aggressively**: Reranking scores are expensive and often repeated
5. **Monitor latency**: p99 matters more than mean in production

Choose the reranker that fits your latency budget while meeting accuracy targets!
