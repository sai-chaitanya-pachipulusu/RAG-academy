## Why Chunk Deduplication Matters in Production

Redundant chunks waste context window space and can confuse the LLM. Deduplication ensures each piece of context adds unique information. In production RAG systems, deduplication is essential for:

- **Context efficiency**: Fit more unique information in limited window
- **Answer quality**: Reduce repetition and contradiction in LLM responses
- **Cost optimization**: Fewer tokens = lower LLM costs
- **User experience**: More diverse, comprehensive answers

### Real-World Scenario

Consider a RAG system answering "What are the benefits of exercise?" from a health database:

- **Without deduplication**: 
  - Chunk 1: "Exercise improves cardiovascular health..." (score: 0.95)
  - Chunk 2: "Exercise improves cardiovascular health..." (score: 0.94) - duplicate!
  - Chunk 3: "Exercise improves cardiovascular health..." (score: 0.93) - duplicate!
  - Wasted 60% of context window on same information

- **With deduplication**:
  - Chunk 1: "Exercise improves cardiovascular health..." (kept)
  - Chunk 4: "Exercise reduces stress and anxiety..." (score: 0.88)
  - Chunk 5: "Regular exercise strengthens bones..." (score: 0.85)
  - Maximum information diversity in context window

## The Mathematical Foundation

### Similarity-Based Deduplication

```
For each pair of chunks (a, b):
  similarity = cosine_similarity(embedding_a, embedding_b)
  if similarity > threshold:
    mark as duplicate, keep higher-scoring chunk
```

### Threshold Selection

| Threshold | Behavior | Use Case |
|-----------|----------|----------|
| 0.95+ | Aggressive | Very similar documents, strict dedup |
| 0.85-0.95 | Moderate | General RAG, balanced approach |
| 0.75-0.85 | Conservative | Diverse sources, preserve near-dupes |

### Complexity Analysis

Naive pairwise comparison: O(n²) for n chunks

Optimizations:
- **LSH (Locality Sensitive Hashing)**: O(n) for approximate
- **HNSW indexing**: O(n log n) for exact
- **Early termination**: Stop comparing when similarity drops

## Theoretical Deep Dive

### Types of Duplication

| Type | Example | Detection Method |
|------|---------|------------------|
| **Exact** | Identical text | Hash comparison |
| **Near-exact** | Whitespace differences | Normalized hash |
| **Semantic** | Same meaning, different words | Embedding similarity |
| **Structural** | Template with different values | Pattern matching |

### The Diversity-Redundancy Tradeoff

```
Context Value = Information Gain - Redundancy Penalty

Where:
- Information Gain = unique facts per chunk
- Redundancy Penalty = similarity to already-selected chunks
```

### Connection to MMR

Deduplication is related to Maximal Marginal Relevance (MMR):

- **MMR**: Select diverse set from candidates
- **Deduplication**: Remove duplicates, then select

Can be combined: deduplicate first, then apply MMR for final selection.

## Production Considerations

### Incremental Deduplication

For streaming/online systems:

```typescript
class IncrementalDeduplicator {
  private seenEmbeddings: Embedding[] = [];
  
  async process(newChunk: Chunk): Promise<boolean> {
    // Check against seen embeddings
    const isDuplicate = await this.checkDuplicate(newChunk);
    if (!isDuplicate) {
      this.seenEmbeddings.push(newChunk.embedding);
    }
    return !isDuplicate; // true if kept
  }
}
```

### Hierarchical Deduplication

Deduplicate at multiple levels:

1. **Document level**: Exact duplicates
2. **Chunk level**: Near-duplicates
3. **Sentence level**: Redundant sentences within chunks

### Metadata Preservation

When deduplicating, preserve:
- Original source document
- All citation information
- Aggregate statistics (how many duplicates existed)

### Validation Checklist

- [ ] Empty input returns empty result
- [ ] Exact duplicates (similarity = 1.0) correctly identified
- [ ] Threshold comparison uses correct operator (>= or >)
- [ ] Keep strategy respected (highest score, longest, first)
- [ ] Statistics calculated correctly

- [ ] Metadata preserved in kept chunks

## Common Pitfalls

- **O(n²) complexity for large result sets**: Use LSH or blocking for large n
- **Setting threshold too low**: Aggressive deduplication loses information
- **Not handling embedding dimension mismatch**: Validate before computing similarity
- **Ignoring score in duplicate selection**: Higher-scoring chunks should be preferred
- **Memory bloat**: Don't store all pairwise similarities
