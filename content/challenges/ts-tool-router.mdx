## Why Tool Routing Matters in Production

Agentic RAG systems need to decide: search documents? Calculate something? Search the web? Tool routing is the first step in every agent loop. Good routing:

- **Optimizes latency**: Skip unnecessary tools
- **Reduces costs**: Avoid expensive API calls
- **Improves accuracy**: Use right tool for the job
- **Enables autonomy**: Agent decides actions

### Real-World Scenario

User queries and optimal tools:

| Query | Tool | Why |
|-------|------|-----|
| "What is RAG?" | document_search | Knowledge question |
| "Calculate 15% of $85" | calculator | Math operation |
| "What's the weather in Paris?" | weather_api | Real-time data |
| "Search for recent AI papers" | web_search | Current information |
| "Compare Python and JavaScript" | document_search + web_search | Hybrid |

**Without routing**: Try all tools sequentially → slow, expensive
**With routing**: Select best tool(s) → fast, targeted

## The Mathematical Foundation

### Tool Selection as Classification

```
Query Features → Classifier → Tool Probability Distribution

Features:
- Keywords (calculate, search, compare)
- Question type (what, how, when)
- Entities (numbers, locations, dates)
- Intent patterns
```

### Confidence Scoring

```
tool_score = keyword_match × 0.4 + 
             pattern_match × 0.3 + 
             embedding_similarity × 0.3

Select tool with highest score above threshold.
```

### Multi-Tool Selection

```
Single tool: argmax(tool_scores)
Multiple tools: tools where score > threshold
```

### Fallback Strategy

When confidence is low:

```typescript
if (maxConfidence < threshold) {
  // Options:
  1. Ask user for clarification
  2. Use default tool (document_search)
  3. Try multiple tools in parallel
  4. Escalate to human
}
```

### Tool Chaining

Some queries need multiple tools:

```
"Weather in the capital of France"
→ 1. search("capital of France") → Paris
→ 2. weather("Paris") → result
```

## Production Considerations

### Latency Budget

Routing must be fast (<5ms):

```
Total: Routing (5ms) + Tool execution (100ms) = 105ms
vs: Sequential tools (400ms)
```

Use lightweight methods (regex, heuristics) not LLM-based routing.

Implement a tool router:

  name: string;
  description: string;
  keywords: string[];

interface RoutingResult {
  selectedTools: string[];
  confidence: number;
  reasoning: string;
}

interface RouterConfig {
  confidenceThreshold?: number;  // Default: 0.6
  maxTools?: number;             // Default: 1
  allowMultiple?: boolean;       // Default: false
}

class ToolRouter {
  private tools: Map<string, Tool>;

  constructor() {
    this.tools = new Map();
  }

  registerTool(tool: Tool): void {
    /**
     * Register a tool for routing.
     */
    this.tools.set(tool.name, tool);
  }

  route(query: string, config?: RouterConfig): RoutingResult {
    /**
     * Route query to appropriate tool(s).

     * Args:
     *   query: User query
     *   config: Routing configuration

     * Returns:
     *   RoutingResult with selected tools and confidence

     * Algorithm:
     *   1. Score each tool based on keyword matches
     *   2. Score based on description similarity
     *   3. Combine scores
     *   4. Select top tool(s) above threshold
     *   5. Return with reasoning
     * 
     * Scoring:
     *   - Keyword match: +0.3 per matching keyword
     *   - Pattern match: +0.5 for strong patterns
     *   - Description similarity: embedding cosine sim × 0.4
     * 
     * Edge Cases:
     *   - No tools registered: return empty
     *   - No tool above threshold: return default or ask

## Common Pitfalls

- **Over-matching on common words**: "the", "a" shouldn't match
- **Not having a default/fallback tool**: Always have backup
- **Too many tools returned**: Limit to most relevant
- **Ignoring tool dependencies**: Some tools need others first
- **Not caching routing decisions**: Same query → same tool
